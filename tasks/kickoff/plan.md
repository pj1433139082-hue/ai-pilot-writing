## 技术选择

1. **改动落点**：真实文件就地改，不新建第二份副本。理由：P0 判据单源是既有铁律（`SKILL.md:91-93`），任何"在新项目里放一份"的方案都会立刻破坏单源约束。
2. **新项目只做"台账 + 验收"**：本项目仓库不复制 skills/vault 内容，只记录改动与证据。理由：复制会立刻产生第二份判据、第二份格式规范（`out_of_scope` 已明列禁止）。
3. **提案 9 用「加一环」而不是「改触发器」**：触发器 `069eafb0dd4d` 是 agent 作业，正文质量依赖 LLM；只把**落盘**这一确定性动作交给 17:32 的 no_agent 作业，LLM 负责内容、脚本负责写文件——这正是 `playbook.md:187` 三条口径第 1 条「写盘归脚本，内容归模型」。不选「改 prompt 让 LLM 一定写盘」，因为 10-11 已证明自觉性靠不住；不选「把触发器整体改 no_agent」，因为正文生成不是确定性任务。
4. **回退分支保留**：`aar-push-dingtalk.py` 的 FALLBACK（读 cron 输出 `## Response`）已在 10-12/10-14 救过场，新拓扑未跑通稳之前不删。
5. **索引重建用脚本生成再人工核**：`工具地图.md` 88 条链接逐条手写风险高（已出 2 处断链），先用一次性脚本从目录结构生成骨架，再人工补每篇一句作用。
6. **P1 阈值改法选密度而非提高绝对值**：`缓存×31` 这类词在主题文里天然高频，绝对值抬高只是把阈值推高，下个月又全中；密度 + 概念词白名单同时给出，才可能长期有效。
7. **不碰调度时间表**：`out_of_scope` 第 4 条已排除改时间表与作业集合；T3 只新增一个 17:32 写盘作业，不改任何既有钟点。

## 风险

1. **改 jobs.json 影响在跑的链**（高）：17:32 是新钟点，插在 17:30 触发器与 17:45 推送之间。应对：先落脚本并本地验证三路径，再上作业；上线后盯 `executions.db` 里 `069eafb0dd4d` → 新作业 → `50dd3d2e5f57` 三格是否连续三天 completed；任何一格异常就回退到「触发器照旧 + 推送回退保留」的原状态。
2. **改 `article_lint.py` 影响发布门禁**（高）：`quality_check.py` 与 `article-triage.py` 共用它。应对：只改 P1 段落，P0 代码行一格不动；改前后对同一批 10 篇做输出 diff，P0 条数必须完全一致。
3. **P1 降噪可能掩盖真问题**（中）：白名单概念词写宽了会把真重复也豁免。应对：白名单显式列名并写清理由，随 `article_lint.py` 一起改，不做通配；降噪后仍保留「软词」「来源链接偏少」「无来源小节」三类与阈值无关的告警。
4. **两篇 draft 处置与用户预期不符**（中）：10-02 改稿会动用户可能已看过的稿子。应对：只删无出处表述，不改论证与结构；改动前后把摘要段与折算段原文贴进 `progress.md` 供对照。
5. **索引重建量大易漏**（中）：100 篇一次性重写，中途被打断会留下半新半旧的索引。应对：先写脚本生成到临时文件，核对通过再整体覆盖；验收脚本要求链接目标 100% 存在。
6. **Cloudflare 挡官方页**（低）：`platform.openai.com` 与 `openai.com/index/api-prompt-caching/` 本轮均 HTTP 403，无法直接引官方页。应对：T1.2 只删无出处表述、不新增任何需要外部核实的数字，故不依赖被挡的页面；web 侧只作背景，不作为稿内出处。
7. **vault 仓库有他人未提交改动**（低）：`paper_work` 工作树含上一会话遗留改动。应对：只碰 `已写清单.md`、`playbook.md`、`资料库\AI工具\` 下文件，不 git add / commit / push。
